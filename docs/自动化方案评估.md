# 自动化方案可行性评估

记录「分享日签 / 看广告 / 阅读时长」三类任务，在不同自动化路线下的真实可行性。
结论基于对掌阅 8.7.4 APK 的静态分析与接口实测（2026-10-28）。

> **更新（2026-11-10）**：「阅读赚代金券」10 档的时长已改为**纯 HTTP 可行**——
> 福利计数实际由掌阅网页版 `pc.ireader.com` 的上报接口驱动，实现为 `src/ireader_welfare/reading.py`，
> 详见 [阅读时长方案.md](阅读时长方案.md) 第九节。下文涉及阅读时长的旧判断已同步修正；
> 分享日签与看广告的结论不变。

## 一、目标任务的完成判定机制

| 任务 | 完成动作 | 判定信号来源 | 是否经过 HTTP |
|------|----------|--------------|---------------|
| 分享日签 | `downloadImage()` 原生桥弹系统分享面板 | 客户端在分享链路内自行上报 | 否 |
| 看广告 | 穿山甲/优量汇激励视频播放完成 | 广告 SDK 回调 `jrttRewardVideoResoultEvent` | 否 |
| 阅读时长 | 网页版阅读器逐分钟上报 | 网页版 `read/time` 上报才是福利计数来源（手机端 postal 上报无效） | 是，纯 HTTP 可行 |

## 二、APK 环境检测现状

APK 未加固（无 360/乐固/梆梆等壳），但内置完整的环境检测清单：

| 检测类型 | 关键词（dex 内出现次数） |
|----------|--------------------------|
| 模拟器 | `bluestacks`(39) / `vbox`(34) / `nox`(18) / `mumu`(5) / `genymotion`(5) / `qemud`(1) / `tiantian`(4) |
| Root | `magisk`(5)、`/sbin/.magisk/`、`/sbin/.core/` |
| 注入框架 | 常见注入框架特征、`/proc/self/maps` |
| 调试 | `ro.debuggable` |

模拟器特征文件清单（dex 内硬编码）：
```
/proc/irq/9/vboxguest        # VirtualBox（雷电/MuMu 底层）
/init.nox.rc                 # 夜神
/init.vbox86.rc              # VirtualBox
/fstab.vbox86
/etc/mumu-configs
/mnt/prebundledapps/bluestacks.prop.orig   # 蓝叠
/mnt/sdcard/bstfolder/
```

**判定**：这套清单是通用的环境检测库（覆盖市面上几乎所有模拟器），不针对某一款。意味着任何模拟器都需额外做特征隐藏。

## 三、各路线可行性

| 路线 | 分享日签 | 看广告 | 阅读时长 | 说明 |
|------|----------|--------|----------|------|
| 纯 HTTP | ✗ | ✗ | ✓ | 阅读时长走网页版 `read/time`（2026-11-10 实测，见 [阅读时长方案.md](阅读时长方案.md) 第九节）；分享/广告的完成信号不经 HTTP |
| uiautomator2 点真机 | ✓ | ✓（需额度） | ✓ | 最可靠，模拟真人点击 |
| 模拟器 + UI 自动化 | 部分 | ✗ | ✓ | 分享可弹面板，广告受 IVT 风控 |
| 运行时 Hook 客户端函数 | ✓ | 部分 | ✓ | 需 root 并绕过 App 的注入检测，维护成本高 |
| 无 Root 抓包改包 | ✗ | ✗ | ✗ | TLS + 签名双重保护 |
| 真机自建无障碍服务 | ✓ | ✓ | ✓ | 稳定性最高，开发量最大 |

### 路线详解

**1. uiautomator2 驱动真机（推荐）**

通过 adb 操作真实手机，点击真实按钮、播放真实广告、触发真实分享。
优势：所有原生检测天然通过；劣势：需一台闲置安卓机长期接着。

**2. 模拟器 + UI 自动化**

分享日签可行（面板能弹，可选系统分享）；阅读时长可行（只要客户端计时器在跑）；
广告不可行 —— 广告 SDK 有无效流量（IVT）风控，模拟器常被判定无效，广告要么不加载、要么播完不给回调。

需配合模拟器特征隐藏（改 `ro.product.*`、删 `vboxguest` 相关、Magisk Hide 等），工作量与成功率都不确定。

**3. 运行时 Hook 客户端函数**

在客户端内部直接投递「任务完成」信号，跳过真实的分享面板与广告播放。
理论上最强，但需要 root 设备，且 APK 内置注入检测，属于对抗性较强的手段——
App 一升级、类名或方法签名一变就可能失效，维护成本高。
本项目不提供实现，仅作为技术方向的记录。

**4. 无 Root 抓包改包**

不可行。业务接口有 `sign` 签名（SHA1WithRSA，密钥在 so 内），且走 TLS。
改包后签名失效；重签名又需要拿到私钥，而私钥在 native 层。

**5. 真机自建无障碍服务（AccessibilityService）**

自己写一个 Android 无障碍 App，监听福利页、自动点按钮。
优势：不用 root、不用 adb、不触发 root 检测（无障碍是官方 API）；可常驻后台。
劣势：开发量最大（需写 Android 工程），无障碍权限需手动授予。

## 四、成本收益对照

以「每天稳定拿到分享日签 20 代金券 + 阅读档位」为目标：

| 方案 | 前期投入 | 稳定性 | 每日操作 |
|------|----------|--------|----------|
| 现有 HTTP 脚本 + 手动分享 | 已完成 | 高 | 点一次分享 |
| uiautomator2 + 闲置真机 | 2~3 小时 | 高 | 全自动 |
| 模拟器 + 特征隐藏 | 数小时~数天，成功率不确定 | 低 | 全自动 |
| 无障碍 App | 1~2 天 | 高 | 全自动 |

## 五、结论

- **阅读时长（10 档）**：纯 HTTP 已跑通（网页版接口，见 [阅读时长方案.md](阅读时长方案.md) 第九节），无需真机、无需 root
- **分享日签**：完成信号在原生分享链路，HTTP 伪造不了；可行路线为真机 UI 自动化（`src/share_daily.py`）或运行时 Hook（需 root，本项目未提供实现）
- **看广告**：当前账号服务端未开放额度（`show:false`），即使全自动也无广告可看；开放后仍受 IVT 风控限制，模拟器大概率无效

## 六、合规提示

上述自动化均可能违反掌阅用户协议。仅建议用于自己账号的便利性操作，避免高频调用与批量账号操作，以免触发风控。
