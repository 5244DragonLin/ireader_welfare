# 阅读时长任务方案

讨论「阅读赚代金券」这 10 档（需读 2/5/10/15/20/30/45/60/120/180 分钟，全领 505 代金券）
的分钟数能不能绕开真实阅读拿到，以及每条路线的成本。

> **重要更新（2026-11-10）：问题已经解决，走 PC 网页版接口即可，纯 HTTP、不需要设备。**
> 见文末「九、已跑通的路线」。下面第一至第八节是早期摸索过程，保留作记录。

结论以现有实测为准：目前没有一条路线被验证能稳定增加这部分分钟数，
原因不是「协议拿不到」，而是**还没确认服务端从哪里取这个数**。

手头设备未 root，因此运行时 Hook 相关路线（改客户端内存、改报文）暂时走不通，
当前主线改为两条：用 `read_probe.py` 查清新版接口的口径，用 `read_keep.py` 走真机挂机。
下面第二节、第三节是为将来有 root 设备时留的记录。

## 一、现在的判断和它的证据强度

逆向笔记里写着「`/postal/reading_time/report` 与福利计数是两套数据源」。
这个结论来自两次实验：

| 实验 | 接口返回 | 福利任务 current |
|------|----------|------------------|
| 伪造 8 分钟（`bid=0`） | `code:0` | 仍为 0 |
| 伪造 120 分钟（`bid=真实书ID`） | `code:0` | 仍为 0 |

两次都只验证了「旧接口 `current` 没动」。这不能排除另外三种解释：

1. 计数确实来自另一个上报入口，`reading_time` 只服务阅读统计（排行榜、阅读等级）。
2. 计数同源，但伪造的报文被服务端丢弃。可丢的点很多：`res` 为空、位图里包含
   尚未发生的分钟、单次增量过大、`bid` 与阅读进度不匹配、设备指纹与 zysid 不一致。
3. 计数同源且报文受理，但走批量汇总，`current` 延迟更新（小时级或次日）。

三者对应的做法完全不同，所以下一步不是继续伪造，而是先定位数据源。

## 二、一个此前漏掉的接口

福利 H5（`ah2.zhangyue.com/activity/welfareIreader.html`）的 `welfareIreader.7f3eab6a.js`
里有两组阅读接口，按 `isNewActivity` 二选一：

```js
getReadInfo   = () => a("/welfare/sign/v2/read")            // 旧版，本项目一直在用
getReadInfoV2 = () => a("/welfare/market/task/read_get")    // 新版，本项目未使用
```

对应的领奖接口也不同：旧版 `/zycl/newsign/task/draw`，新版 `/welfare/market/task/read_reward`。

本项目只调过旧版。新版接口的返回体结构未知，而它很可能直接带出分钟数的来源字段
（活动 id、统计口径、当日/整期累计方式）。这是当前信息量最大、成本最低的一个查询点，
`src/read_probe.py --dump` 就是为它写的。

## 三、没有 root 时能做的定位

这一节是当前可执行的部分，全部不需要 root。

| 手段 | 需要什么 | 能回答什么 |
|------|----------|------------|
| `python src/read_probe.py` | 账号 | 新版 `read_get` 有没有返回体，字段里有没有统计口径 |
| `python src/read_probe.py --watch 300` | 账号 + 手机 | 读书时分钟数何时开始变：实时、延迟，还是压根不变 |
| `adb logcat` 过滤 `zhangyue\|ireader\|reading` | USB 调试 | 客户端有没有把上报 URL 或分钟数打进日志 |
| 无 root 抓包（Reqable 等） | — | 解不开密。见下文 |

`read_probe.py --watch` 是最省事的一条：不需要注入，不修改任何东西，
只要在手机上读几分钟，就能看出旧接口 `current` 是否跟随。若不跟随，
再跑一次听书 10 分钟做对照，就能区分「只认阅读」「听书也算」「完全不按真实行为计」。

### 为什么手机装 Reqable 抓不到

不是工具的问题，是 Android 的证书信任机制。从 Android 7.0 起，应用默认只信任
系统证书区（`/system/etc/security/cacerts/`），装在用户证书区的 CA 一律不认，
HTTPS 握手直接失败。这么设计正是为了防中间人抓包。

Reqable 官方文档也这么写，它给出的免 root 方案只有一条：**改目标 App 的源码**，
在 `network_security_config.xml` 里声明信任用户证书后重新打包。
这对掌阅不成立——拿不到源码，也没有重新签名的能力。

有两个例外，可以花几分钟排除：

- 掌阅自己留了信任用户证书的配置。国内部分 App 为方便测试会留这个口子，
  验证方式是装证书后开抓、读一页书，看有没有请求解密成功。若全是 CONNECT 失败，就是没有。
- 沙盒路线：VirtualXposed 内克隆掌阅，配 Reqable 官方的 TrustMe 模块。
  原理是容器在进程内替换证书校验，不需要 root。但 VirtualXposed 对 Android 9 以后的
  系统支持很差，现代手机基本装不上；掌阅本身又有 xposed / 注入检测。成功率低。

即使解不开密，Reqable 仍能看到「连了哪些域名、什么时候连、流量多大」，
这本身有用——可以回答「读书时到底有没有请求发出去」，比现在完全黑盒强。

要用系统证书区，只有三条路：root 手机、模拟器、云手机。
其中阿里云无影云手机的 adb 连接后默认就是 root，华为云有 root 版镜像并提供「真机指纹」开关，
是在不占本机内存的前提下唯一能把运行时 Hook 和抓包同时跑通的方案。

## 四、决定性实验（需 root，暂缓）

准备：一台已 root 的 Android 真机，装有掌阅并已登录；Hook 工具版本与设备端一致。

步骤：

1. 记下基线：`python src/read_probe.py --dump`，保存两套接口的原始 JSON。
2. 注入只记录、不改包的脚本，抓全部发往 `zhangyue.com` / `ireader.com` 域名的请求
   （URL、方法、body 长度与前 200 字节、时间戳）。
3. 用 `python src/read_probe.py --watch 300` 开一个轮询窗口，每 15 秒采一次。
4. 在 App 内打开一本带「品质好书」标记的书，真实阅读 3 分钟，翻 2 页。
5. 退出阅读，等 60 秒，停止记录。

判读：

| 观察结果 | 说明 | 下一步 |
|----------|------|--------|
| `current` 在阅读期间就涨，且抓到对应分钟数的请求 | 计数同源，入口就是这个请求 | 按该请求的字段逐项比对伪造报文，做增量构造 |
| `current` 不动，但抓到了 `reading_time` 上报 | 计数另有来源 | 在新版 `read_get` 返回体里找统计口径，或找阅读会话开始/结束接口 |
| 读完当时不动，隔一段时间才涨 | 批量汇总 | 只需解决报文受理，不必管实时性 |
| 抓不到任何上报 | 客户端本地累加，退后台或切书时才发 | 记录点改到「退出阅读器」时刻 |

第 4 步必须用带「品质好书」标记的书，因为日常任务名就是「阅读品质好书满5分钟」，
存在按书单过滤的可能。若用普通书读 3 分钟 `current` 不动、换品质好书才动，
就能确认过滤口径——那样伪造报文的 `bid` 必须落在书单内。

## 五、若确认可以伪造，报文构造要点

不要一次性把整天的位图刷满。旧实验正是这么做的（120 分钟一把梭），
即便同源也极易被丢弃。可行方向：

- 位图只标记「当前时刻往前推 N 分钟」的连续区间，N 从 2 开始，逐次加 3～5 分钟。
- 每次报完立刻查一次 `current`，以它是否跟随作为唯一判据，不看 `code`。
- `bid` 用自己书架里确实打开过的书，`res` 从真机抓到的一次真实请求里抄，不要留空。
- 保留一次真实请求的完整报文作模板，之后只改位图与时间戳，签名用现有 `crypto.py` 重算。
- 遇到「报完不跟随」就停在该增量上，不要继续加量，否则容易踩到异常检测。

`/postal/reading_time/report` 的签名细节（除 `usr`/`zysid` 外还带哪些参数、
是否整体签名）在逆向笔记里没有落到字段级，重新实现上报前需要补这部分。

## 六、不需要伪造的路线（当前主线）

如果目标只是把 505 代金券拿到，真机挂机比伪造更省事，也没有报文被丢弃的问题。
下面两条都由 `src/read_keep.py` 执行，全程只用 adb，不需要 root。

- 阅读器挂机：插电并设常亮（`svc power stayon usb`），打开一本品质好书，
  脚本每 30～60 秒 `input swipe` 翻一页。180 分钟对应 3 小时，全天档位可拿满。

  ```bash
  python src/read_keep.py --check                          # 先看设备与当前分钟数
  python src/read_keep.py --run --minutes 180 --interval 60
  ```

- 听书：日常任务里「收听品质好书满10分钟」是独立任务。若听书也计入阅读档位，
  就不必翻页、可以息屏整晚播放，成本最低。这一条尚未验证，验证方式很轻——
  挂 10 分钟听书，看 `current` 是否 +10，脚本会直接给出转化率：

  ```bash
  python src/read_keep.py --run --minutes 12 --mode listen
  ```

  结束那行「听书计入阅读时长」出现，就说明可以息屏挂整晚。

这两种方式都是真实行为，没有伪造报文，唯一的特征是长时间无操作，
建议每天只挂一到两次，不要连续多日通宵。

## 七、在电脑上操作

本机内存占用由小到大：

| 方案 | 本机内存 | 成本 | 现状 |
|------|----------|------|------|
| 手机 + 无线 adb | 几乎为零，只跑 adb 客户端 | 0 | 可用，`read_keep.py --tcpip` / `--connect` |
| 云手机（华为云 CPH、阿里云无影） | 几乎为零 | 按实例计费 | 支持 `adb connect`，ARM 容器而非 x86 模拟；阿里云 adb 连上默认就是 root，华为云有 root 版镜像与「真机指纹」开关；仍可能被识别为虚拟设备 |
| WSA | 2GB 起 | 0 | 2025-03-05 停服，运行组件已被禁用，不可用 |
| 雷电 / MuMu 等模拟器 | 2～4GB | 0 | APK 内置模拟器特征检测，需额外隐藏 |

无线 adb 的做法：先用 USB 连一次，切到无线，之后拔线，手机放一边充电，
电脑侧只发送翻页与查询指令。

```bash
python src/read_keep.py --tcpip                      # 切无线，看到 adb connect 成功即可拔线
python src/read_keep.py --connect 192.168.1.5:5555 --run --minutes 180
```

手机重启后无线 adb 会失效，重新 `--connect` 一次。云手机把厂商给的
`IP:端口` 填进 `--connect` 就是同一条路径。

### 免费云手机与本地虚拟机

云手机没有真正免费无限时长的档位——算力和带宽是硬成本。常见形式是新人几小时试用、
每日签到领 1～3 小时、看广告续时长。各平台宣传数字互相矛盾（同一家在不同文章里
既写「新人 24 小时」又写「6 小时」），只能当参考，需要自己注册核实。

更关键的是免费档基本不给 root，所以免费云手机只能当挂机设备，当不了研究设备——
抓包和运行时 Hook 仍然做不了。而 180 分钟/天 的阅读档位，恰好卡在多数免费额度上限之上。

零成本拿到 root 环境还有一条路：VMOS Pro。它在手机本地跑第二套安卓，
自带 root，可装 Xposed / Magisk / LSPosed，支持息屏后台保活。把 CA 证书写进
`/system/etc/security/cacerts/` 就能抓包，也可以用 Reqable 的 TrustMe 模块。
代价是 ROM 只到 Android 7.1，掌阅 8.7.4 未必装得上；掌阅本身也有虚拟机特征检测。
建议只用官方版，各类「解锁会员」的修改版来源不可靠。

官方 PC 客户端这条路不存在：掌阅的电脑版都是第三方用模拟器打包的，
没有带福利中心的 PC 版，所以 PC 端读书无法完成福利任务。

纯 Python 直接上报仍然是「零设备、零占用」的唯一终极形态，但卡在拿不到一次真实报文——
报文里的 `res` 等字段需要从客户端抓一次真值，而无 root 抓不了 HTTPS。这条路要有 root 设备才谈得上。

## 八、风险

三条路线都会留下与正常使用不同的行为特征：伪造报文是请求内容异常，
挂机是长时间无操作阅读。掌阅可能据此限制领取或封号，且规则随时会变。
只在自己账号上低频使用。

## 九、已跑通的路线：PC 网页版上报接口（2026-11-10 实测）

上面「PC 客户端这条路不存在」的判断需要修正一半：**官方 PC 客户端确实没有，
但掌阅官方网页版（`pc.ireader.com`）一直在上报阅读时长，而且它认账号。**

实测当天用这套接口把 10 档全部拿满、505 代金券当日到账，
全程没有手机、没有 root、没有运行时 Hook、没有 adb。实现为 `src/ireader_welfare/reading.py`。

### 9.1 接口

```http
POST https://api-pc.zhangyue.com/bookstore/open/read/time
     ?usr=&zysid=&p29=zye5b814&p2=104583&p3=101010010&p4=501603&p33=com.chaozh.iReaderFree

{
  "book_id":    "10121980",
  "local_bid":  "",
  "start_time": 1794302449753,   // 毫秒
  "end_time":   1794302749753,   // 毫秒
  "res":        "R",
  "time_stamp": 1794302749753,
  "date":       20261110,
  "switch":     1,               // 0=阅读中定时上报, 1=结束上报
  "app_id":     "zye5b814",
  "user":       "i1086644292"
}
```

它**不是**手机端那个 `/postal/reading_time/report`：
没有 GZIP、没有 BASE64 分钟位图、**也不需要 RSA 签名**，`usr`/`zysid` 放在 query 里即可。

### 9.2 服务端怎么算

网页版阅读器每 60 秒调一次（`switch=0`），退出阅读时再调一次（`switch=1`），
每次只报「刚刚这一分钟读了这本书」。服务端把区间落成分钟集合，再累加。

实测出来的三条规则：

| 现象 | 结论 |
|------|------|
| 报 6 分钟、其中 2 分钟与早先上报重叠 → `current` 只 +4 | **按分钟去重**，重复时段不重复计 |
| 一次报 30 分钟非重叠区间 → `current` +31 | 单次区间长度不限 |
| 一次报 142 分钟非重叠区间 → 直冲 180 档 | 单日可拿满 |
| 报未来时段 / 不存在的 `book_id` → 仍返回 `code:0` | 校验很松，但**不构成本项目该依赖的能力** |

`code:0` 依然不能当成功依据 —— 老规矩，看 `v2/read` 的 `current` 才算数。

### 9.3 与「日常任务」不同源（已排查，非未验证）

`/welfare/sign/v2/task` 里的日常任务与 10 档代金券**不是同一套计数器**，
且已排除所有能从 HTTP 侧想到的入口：

| 尝试 | 结果 |
|------|------|
| 阅读档位报满 180 分钟后看日常任务 | `阅读品质好书` 仍 `current=0` |
| 换另一本出版书（12482413 / 10007034）重报 40 分钟 | 仍 0 |
| 用 App 的 `p3=18070403` + `switch=0` 走同一接口 | 仍 0 |
| `/zycl/newsign/task/report`（传 20017 / 263+20017 / 各种组合） | 一律回「获取奖励成功」，任务 `current` 不变 → **空壳** |
| `/zycl/welfare/task/accept` + `/task/finish` | `任务不需要领取` / 返回 `[]`，状态不变 → **空壳** |
| 手机端 `/postal/reading_time/report`（带 GZIP 位图，含不签名与带签名两种） | 回 `code:0`，日常任务仍 0；**且对不存在的 `usr` 也回 `ok`** → 空壳 |
| 检查 `pc.ireader.com` 的 JS 包 | 里面**没有任何** welfare / task 接口，只有埋点 `logv2.ireader.com` |

**最强证据**：对着任务列表反复观察，只有这两条的 `current` 在阅读档位满 180 分钟后
依然纹丝不动；而同一列表里其它任务的行为各不相同（见下方更正），
说明它们是独立的计数器，不是同一个阅读统计派生出来的。

> **更正（2026-11-10 晚）**：这里原先写着「同一时刻『打开掌阅APP』任务的 `current` 也是 0，
> 说明整套日常任务都由 App 侧行为驱动」。这条推理**不成立**——
> 「打开掌阅APP」是 `mode=0`、`quota=1` 的任务，它的 `current` 恒为 0，
> **真正表示完成的是 `status`**。而且它后来确实被纯 HTTP 触发了（见
> [掌阅逆向笔记](掌阅逆向笔记.md) 的日常任务排查表）。
> 「阅读/收听」这两条 `current` 不涨是实测事实，但别再用「打开APP 也是 0」当论据。

结论：这 20 活跃值（阅读 10 + 收听 10）目前**只能靠真机在 App 内完成**。
它不在网页版上报接口的能力范围内；若要拿，仍得回到 `read_keep.py` 那条真机路线。


### 9.4 用法

日常由 `main.py run` 自动完成（先铺时长再领奖），无需单独操作：

```bash
python src/main.py run                             # 一条龙：铺 180 分钟 → 签到 → 领奖 → 抽奖 → 开箱
python src/main.py run --read-pc-minutes 30        # 只铺 30 分钟
python src/main.py run --no-read-pc                # 跳过铺时长
```

上报状态记在 `output/read_pc_state.json`，重跑自动避开已报时段，
不会把分钟浪费在重复区间上；窗口只铺在「今天零点到当前时刻」之间，不会报未来时间。
实现为 `src/ireader_welfare/reading.py`。

### 9.5 风险

比挂机轻，但仍不是正常行为：请求来自非常规客户端、间隔机械、
且接口对 `book_id` 与时间戳几乎不校验——这些都是服务端随时可以收紧的点。
建议每天一次、只用自己账号，不要多账号批量跑。

## 十、阅读时长抽奖（每天 4 次，与大转盘是两个活动）

阅读时长除了发代金券，还发抽奖机会：读完 30 / 60 / 120 / 180 分钟各解锁 1 次，
每天最多 4 次。页面标题是「阅读时长抽奖~~~」，福利页「去抽奖」按钮跳的就是它。

**它和大转盘不是一个活动**，这点很容易搞混：

| | 大转盘（福利页九宫格翻牌） | 阅读时长抽奖 |
|---|---|---|
| 活动号 | `activeId=12516`（随账号/期次下发） | `activeId=16416` |
| 次数来源 | 签到、日常任务奖励（翻卡机会） | 阅读时长里程碑 |
| 状态查询 | `/welfare/sign/page` 的 `wheel.draw_times` | 抓页面解析 `dataMap` |
| 抽奖请求 | `Activity_NewDzp.Draw` + `activeId` | 同接口，但**必须多带 `actSign`** |

### 10.1 状态查询：只能抓页面

没有 JSON 接口。`Activity_NewDzp.Index` 返回的是服务端渲染的 HTML，
状态塞在 `<div id="dataMap" data-option='{...}'>` 里：

```json
{"isLogin":true,"drawTimes":4,"isActive":true,"actSign":"54890842", ...}
```

**未登录时 `drawTimes` 恒为 0**，所以必须带上 `usr`/`zysid` 再抓，
否则会误判成「没有次数」。

`data-list='[{"t":30,"d":1},{"t":60,"d":1},{"t":120,"d":1},{"t":180,"d":1}]'`
是那 4 个里程碑，领机会时要原样回传。

### 10.2 领里程碑机会

```http
GET https://ah2.zhangyue.com/zyam/app/app.php
    ?ca=Activity_NewDzp.DrawReadAward&activeId=16416&list=[{"t":30,"d":1},...]
```

阅读分钟够了**不会自动到账**，必须调这一次。已领过时返回
`{"code":1,"msg":"领取失败"}`，无副作用，可以放心重复调用。

### 10.3 抽奖

```http
GET https://ah2.zhangyue.com/zyam/app/app.php
    ?ca=Activity_NewDzp.Draw&activeId=16416&actSign=<页面下发的值>
```

返回 `{"code":0,"draw_times":3,"gift":{"desc":"10代金券",...}}`，
`draw_times` 是抽完后的剩余次数。返回码：`0` 成功、`32401` 活动已结束、
`70113` 今日赠送金币达上限。

### 10.4 实测

2026-11-10 当天 4 次全部抽完：2 + 10 + 10 + 2 = **24 代金券**，
代金券总额从 535 变 559，确认到账。

### 10.5 实现

`welfare.py` 里三个方法：`read_lottery_state()` / `read_lottery_claim_awards()` /
`read_lottery_draw_all()`；CLI 命令 `lottery`，并已排进 `run` 一条龙
（转盘之后、开箱之前）。
