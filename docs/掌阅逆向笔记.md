## 一、登录链路

### 请求

```text
POST https://uc.ireader.com/user/slogin/passwd/v2
Content-Type: application/x-www-form-urlencoded
```

| 参数 | 说明 |
|------|------|
| `data` | 双层加密的业务体，见下 |
| `imei` | 设备标识，`86` + 13 位时间戳即可 |
| `ver` / `version_id` | `1.0` / `80740` |
| `channel_id` | `100` |
| `encrypt_method` | `1` |
| `usr` | 手机号（缺失会返回 400） |
| `timestamp` | 毫秒时间戳 |
| `sign` | `SHA1WithRSA(排序参数串)` |

### data 的构造

```text
inner   = {"password": 密码, "user_name": 手机号}
aesKey  = 随机 16 字节（Base64）
Data    = AES/CBC/PKCS7(inner, key=aesKey, iv=aesKey)
AesKey  = RSA/PKCS1v15(aesKey, 硬编码公钥)

data = {"AesKey": AesKey, "Data": Data}
```

注意 **IV 与密钥相同**，这是客户端的一处实现特点（对应原始类 `tools/m.f`）。

### 硬编码公钥

客户端 dex 里有一把 1024 位 RSA 公钥（对应 `account/i.h` 与 `account/f.o`）：

```text
MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQCAqSnnZ9BVOZjIMTkATIn29nM0hLOsQsXlPbqr
GE4CUmDCncVBHdkfEIF73tSKjhYfLuPH1gDtHRKeCC1DQ4uYJL83oeHtXSldGUlfuv9rh0Q/2Hx
l3iG8TUc1drTKTZFfkQWWseTb3vAx8Ggse9xZNTjI6enOEjNyGlAIF+RKrwIDAQAB
```

### native 私钥：4 把里只有第 4 把能用

`libUiControl.so` 里硬编码了 4 把 PKCS8 私钥（1024 位）。用 DER 头 `30 82 ?? ?? 02 01 00` 扫描即可提取。

实测结论：

| 私钥 | 用途 |
|------|------|
| #1 ~ #3 | 登录签名返回 `[null, 6]`（被拒） |
| **#4** | ✅ 登录签名通过 |

抓取方式：

```python
for m in re.finditer(rb"\x30\x82([\x00-\xff])([\x00-\xff])\x02\x01\x00", so_data):
    ln = (m.group(1)[0] << 8) | m.group(2)[0]
    if 300 < ln < 2000:
        key = load_der_private_key(so_data[m.start():m.start() + 4 + ln], password=None)
```

### 返回 token 的解密（最反直觉的一步）

服务端返回的 `token` 有两段：

```json
{"token": {"AesKey": "...", "Data": "..."}}
```

`AesKey` **不是**用私钥解，而是用上面那把**公钥**做 RSA 运算：

```text
m = c^e mod n
→ 去掉 PKCS#1 v1.5 type 1 填充（前两字节 00 01）
→ 得到 Base64 字符串 → b64decode → 16 字节 AES key
```

数学上这等价于验签运算。客户端用「私钥加密、公钥解密」的方式传递对称密钥，所以只能用配对公钥还原。

拿到 AES key 后解 `Data`，明文含：

```json
{
  "flag": 1,
  "rsa_public_key": "<本次会话的 PKCS8 私钥>",
  "device_list": [...],
  "session_id": "<即 zysid>"
}
```

`session_id` 后续所有请求都要带（`zysid` 参数），`rsa_public_key` 是会话签名私钥。

## 二、接口签名规则

所有业务接口统一用：

```text
1. 参数按 key 字典序排序
2. 拼成 k=v&k=v（跳过空值）
3. SHA1WithRSA 签名（客户端私钥）
4. 作为 sign 参数带上
```

### 关键坑：必须带 H5 页面参数

福利中心的多数接口需要附带这些参数，否则返回 `code:0` 但业务不落账：

| 参数 | 真实值 | 含义 |
|------|--------|------|
| `p2` | `104583` | 产品/包标识 |
| `p3` | **`18070403`** | 客户端版本（★ 关键） |
| `p4` | `501603` | 渠道 |
| `p29` | `zye5b814` | 渠道标识 |
| `p33` | `com.chaozh.iReaderFree` | 包名 |

**`p3` 的值来自 `Device.APP_UPDATE_VERSION` 静态字段**，不是随手编的版本号。

> 我在早期分析时用了自造的 `p3=101010010`，结果任务列表一直返回空数组、分享日签额度显示 0。
> 改成 `18070403` 后任务列表立刻有数据。这个错误一度让我误判「服务端未开放任务」。

## 五、阅读时长上报协议

### 请求格式

```text
POST https://uc.ireader.com/postal/reading_time/report
body = GZIP( {"usr": "...", "data": "<字符串化 JSON>"} )
```

`data` 是**字符串**（不是对象），服务端会二次解析。

### data 结构

```json
{
  "20261028": [
    {"bid": 书ID, "local_bid": "", "read_percent": 0.5, "res": "", "d": "BASE64"}
  ]
}
```

### `d` 字段：一张「读过哪几分钟」的位图

这是协议里最精巧的部分：

- `d` = BASE64(byte[])
- **每一位代表 1 分钟**，`1` 表示该分钟在阅读
- **每 8 分钟占 1 字节**

位运算逻辑在 `od/a;->j0([B I I)I` 与 `h0([B I I)I`：

```text
j0(bitmap, startMinute, endMinute):
    算出 start 落在第几个字节、字节内第几位
    逐字节 set bit，最后统计置位数 = 本次新增分钟数
```

构造示例（标记前 8 分钟都读过）：

```python
bits = bytes([0xFF]) + bytes(14)      # 15 字节 = 120 分钟容量
d = base64.b64encode(bits).decode()
```

### 实测结论：上报成功，但福利不认

| 实验 | 接口响应 | 福利任务 `current` |
|------|----------|---------------------|
| 伪造 8 分钟（`bid=0`） | `{"code":0,"msg":"ok"}` | 仍是 0 |
| 伪造 120 分钟（`bid=真实书ID`） | `{"code":0,"msg":"ok"}` | 仍是 0 |

**`/postal/reading_time/report` 与福利中心「阅读赚代金券」是两套数据源。**
前者记阅读统计（排行榜等），后者由服务端另行计算，两者不通。

### ★ 补充（2026-11-10）：福利计数真正的入口是 PC 网页版接口

福利那套计数并非「服务端另行计算」，而是由掌阅网页版 `pc.ireader.com`
的阅读器上报驱动的。抓它的 Nuxt 包即可看到：

```js
// 网页版每 60 秒一次（switch=0），退出阅读时再一次（switch=1）
POST https://api-pc.zhangyue.com/bookstore/open/read/time
     ?usr=&zysid=&p29=zye5b814&p2=104583&p3=101010010&p4=501603&p33=com.chaozh.iReaderFree

{"book_id":"10121980","local_bid":"","start_time":<ms>,"end_time":<ms>,
 "res":"R","time_stamp":<ms>,"date":20261110,"switch":1,
 "app_id":"zye5b814","user":"<usr>"}
```

与手机端 `/postal/reading_time/report` 的区别：

| | 手机端 postal | 网页版 read/time |
|---|---|---|
| 鉴权 | RSA 签名（客户端私钥） | 只校验 `zysid`，**不需要签名** |
| 载荷 | GZIP + BASE64 分钟位图 | 普通 JSON，只报一段起止时间 |
| 驱动福利 10 档 | ✗ 不影响 `current` | ✓ **就是它的计数来源** |

网页版 Nuxt 运行时配置里的固定值（与 App 不同，别混用）：
`appId=zye5b814`、`channelId=104583`、**`p3=101010010`**、`p4=501603`、
`p33=com.chaozh.iReaderFree`，API 网关 `api-pc.zhangyue.com`。

实测规则见 [阅读时长方案.md](阅读时长方案.md) 第九节：按分钟去重、单次区间长度不限。
实现为 `src/ireader_welfare/reading.py`（`main.py run` 会自动调用）。

## 六、分享日签的完整链路（2026-10-28 复核修正）

### 6.1 卡片数据里的 `status` 不是完成状态（★ 重要修正）

`/welfare/sign/today/share` 返回：

```json
{"date":"2026-10-28","desc":"重要的不是过去，而是未来。",
 "doing":"面对未来","img_url":"https://...","status":1}
```

`welfareShareCard.js`（卡片页）里的渲染代码是：

```js
t("span", [ e._v(e._s(1 === e.status ? "【宜】" : "【忌】")) ])
```

即 **`status` 是黄历「宜(1)/忌(2)」标记**，用来在日签卡上印【宜】或【忌】，
和「今天有没有完成分享」完全无关。

> 实测反例：`today/share.status=1`（宜）的同时，
> 任务列表里 `id=12988 分享今日日签` 的 `status=0`（未完成）。
> 早期版本用 `today/share.status==1` 判定「今日已完成」，是**误判**。

**正确判定**：从 `/welfare/sign/v2/task` 里找
`target_list[0].value.share_type == "daily_sign_in"` 的那条，看它的 `status`：
`0` 未完成 / `1` 可领取 / `2` 已领取。

### 6.2 分享链路（H5 → 原生）

```text

  → JavascriptAction.do_command("downloadImage")   # H5 命令总入口（巨大 switch）
  → JavascriptAction.i(JSONObject)                 # 取出 Data 字段
  → s.a()  →  post s$d                             # 生成日签图 → 弹 UIShare 面板
  → 分享完成 → s.b(Z)                              # ★ 中间回调，Z = 是否成功
  → s$c.run()  → 回填 tag（标题/图片/链接…）
  → UIShare.setOnShareSuccessListener(s$c$a)
  → 分享成功 → s$c$a.onShareSuccesss()
  → 注入 JS: "javascript:" + shareCallBack + "()"  → H5 的 dailyCardShareCallBack()
  → dailyCardShareCallBack 只做 $emit("updateTaskList")（重拉列表），无 HTTP 上报
```

关键类：

|----|------|------|

| `...online.JavascriptAction` | `i(JSONObject)` | 处理 `downloadImage` |

| `...online.s$c` | `run()` | 回填 webview tag |
| `...online.s$c$a` | `onShareSuccesss()` | **原生分享成功的终点**，注入 `shareCallBack()` |

### 6.3 是否存在 HTTP 上报？（复核结论：没有）

早先笔记里提到过 `URL_ACCOUNT_SHARE_RESULT = /user/scomm/share_report`
（由 `Platform/Share/b.d()/e()` 调用，签名为 native `Security.hash`）。
本次实测：该接口**对任意签名/任意参数都返回 `{"code":0,"msg":"OK"}`，
连不存在的用户、垃圾 sign、不存在的 `type` 都一样 OK** → 又是幂等空壳，
与 `/zycl/newsign/task/report` 同性质。它不改变福利任务 `status`。

同样的对照测试也确认了这些是空壳（任务 12988 前后始终 `status=0`）：

| 接口 | 返回 | 任务是否变化 |
|------|------|--------------|
| `/user/scomm/share_report` | `code:0 OK` | 否 |
| `/welfare/operation/callback` | `103100 来源不存在`（试 10+ 种 source 均同） | 否 |
| `/welfare/operation/itask/get_token` | `code:0`，能拿到 12988 的 token | 否 |
| `/zycl/newsign/task/report` | `获取奖励成功` | 否 |
| `/zycl/welfare/task/finish` | `[]` | 否 |
| `/zycl/welfare/task/receive` | `任务id不能为空` | 否 |
| `/zycl/welfare/task/accept` | `任务不需要领取` | 否 |
| `/zycl/newsign/task/draw`（提前领奖） | `22021 获取奖励失败` | 否 |

**结论：完成标记只认「原生 UIShare 真正分享成功」这一个信号，没有可用的 HTTP 入口。**
可行的两条路仍是：① 真机点一次真实分享（`src/share_daily.py` 已实现）；② 运行时 Hook（思路见 6.4）。

### 6.4 运行时 Hook 的工作思路（不提供实现）

「伪造分享成功」的关键不是改某个回调的返回值，而是**直接触发 H5 的 JS 回调**。

分享成功的终点是 `onShareSuccesss()`，它的实现本质是往 webview 注入一句 JS
（形如 `javascript:<shareCallBack>()`）。所以思路是：

1. 找到分享成功回调所在的类（8.7.4 里是 `com.zhangyue.iReader.online.s$c$a`）
2. 在分享面板弹出前拦截，主动调用该回调
3. H5 收到 `shareCallBack` 后会重拉任务列表，客户端据此认为分享完成

⚠️ 有两个前提必须清楚：

- **需要 root**，并要先绕过 App 的注入检测（详见第七节的环境检测清单）
- 类名/方法签名随版本变化，8.8.1 已与 8.7.4 不同，App 一升级就要重新定位

> 另外要注意：H5 的 `dailyCardShareCallBack` 只是**重拉任务列表**，
> 「完成」仍由服务端在原生链路里判定。Hook 的价值在于
> **让客户端认为分享成功进而触发后续动作**，而不是绕过服务端。

> 本项目不提供 Hook 脚本。原因是这类实现强依赖具体版本、需要 root 设备，
> 且维护成本远高于收益（分享日签仅 +20 代金券）。此处只保留思路，
> 供有需要的人自行研究。

## 九、`code:0` 不等于成功

分析过程中遇到多处「返回成功但没生效」，记录下来避免重复踩坑：

| 场景 | 现象 | 正确判定方式 |
|------|------|--------------|
| 签到 | 不带页面参数返回 `code:0`，但 `is_sign` 仍为 false | 查 `sign_get` 的 `is_sign` |
| 任务上报 | `task/report` 对任意参数都返回成功 | 查任务 `status` / `current` |
| 开宝箱 | `index=0` 返回 `status:0` 但不消耗资源 | 对比 `user_score` 与 `got` |
| 阅读时长 | 手机端 `postal/reading_time/report` 返回 `code:0` 但不影响福利计数 | 查 `v2/read` 的 `current`；要计入福利须走网页版 `read/time` |

**通用原则**：永远用业务状态兜底校验，不要只看返回码。

### 雷电模拟器 9.5.42

| 段 | 内容 |
|----|------|
| 第一段 | 程序（30 个 exe + 273 个 dll + 2 个 vmdk） |

### 三个日常任务能否绕开真机（2026-11-11 修订）

| 任务 | 奖励 | 判定机制 | PC/HTTP 能否完成 |
|------|------|----------|------------------|
| 打开掌阅APP | +10 经验值 | **客户端冷启动上报**（行为埋点） | **不能** |
| 观看视频 ×10 | 每次 10 代金券 | 原生激励视频 SDK 播完回调 | 不能 |
| 分享今日日签 | +20 代金券 | 原生分享面板回调 | 不能 |

**打开掌阅APP**：⚠️ 本节此前写着「可纯 HTTP 完成」——**该结论已作废**（2026-11-11 反编译 8.8.1 后纠正）。

从任务原始字段看，它不是「访问某个页面」，而是**客户端冷启动上报型埋点**：

```json
{"id": 13901, "name": "打开掌阅APP", "type_id": 263,
 "introductions": "启动就能领，若有问题请彻底关闭应用重启",
 "jump_url": "javascript:void(0);",
 "target_list": [{"quota": 1, "style": 550, "value": {"type": 20036, "page_type": null}}]}
```

三条证据：

| 证据 | 含义 |
|------|------|
| `jump_url: "javascript:void(0);"` | **没有任何跳转页面**——「访问某 URL 就能完成」的假设从根上不成立 |
| `value.type: 20036` | 客户端本地行为埋点类型（非服务端接口调用类型） |
| 文案「启动就能领，若有问题请彻底关闭应用重启」 | 官方说明即「冷启动触发」 |

对应的客户端上报端点是 `/zyboot/datapoint/launchreport` 与 `/zyboot/datapoint/applaunch`（App 启动时上报）。这两个字符串在 dex 里只作为 `Lcom/zhangyue/iReader/app/URL` 的静态字段存在，真正调用点在启动流程内，重放需要客户端凭证与设备指纹。

> **为什么此前误判为「可 HTTP 完成」**：2026-11-10 那次观测到任务翻转，
> 真实原因应是**当天那台设备真机冷启动过 App**（触发了启动上报），
> 而恰好同一时段在跑抽奖页请求，于是把「相关」当成了「因果」。
> 2026-11-11 逐一复现 `Welfare.Index` / `Activity_NewDzp.Index` 等页面（带签名与不带签名）
> 均无法触发，与 `jump_url` 为空的事实互相印证。

**结论**：`WelfareClient.mark_app_open()` 保留，当作「碰运气」的廉价尝试即可，
**不要指望它稳定生效**。要拿这 +10 经验值，真机冷启动一次 App 即可（已实测：冷启动后 35 秒内 status 从 0 翻到 1）。

**观看视频**：`video/status` 返回 `show:false` / `53002`（`VIDEO_NO_CHANCE`），
`video/info` 返回 `50003`（`VIDEO_NOSUPPORT`）。更根本的是播放走原生桥
`do_command → jrttRewardVideo`（穿山甲激励视频），完成判定由 SDK 回调服务端，
**没有任何可以 HTTP 重放的凭据**。PC 包里虽然有 `openRewardVideo` 这个函数，
但它同样是 `do_command` 桥调用，浏览器里 `window.ZhangYueJS` 不存在，直接走失败分支。

**分享日签**：PC 包的 `share` 也是 `do_command → Action:"share"` 桥调用。
`/welfare/sign/today/share` 只下发日签卡（`date/desc/doing/img_url/status`），
其中 `status` 是黄历「宜/忌」而非完成状态，**没有可回放的 share token**。
试过 `/zycl/newsign/task/report` 传 `typeId=19`（分享任务的 type_id）等组合，
一律回「获取奖励成功」但任务状态不变——该接口对任意参数都返回成功，是空壳
（传不存在的 `subTypeId=19999` 也一样）。

**一句话**：这三个日常任务的完成信号都在客户端原生层（分享/广告是 SDK 回调，
打开APP 是冷启动埋点），**纯 HTTP 一个都拿不到**。

### 关于「看广告」

`/zycl/welfare/video/status` 六个 position 全部返回 `show:false`，
`/zycl/welfaremarket/video/info` 返回 `50003 不支持视频`。

这是**服务端没给该账号开放额度**，不是实现方式问题。界面上的按钮不会渲染，没有广告可播。
换任何手段都一样。

> 补充（2026-11-11）：另一种常见提示是「今天可观看视频次数已用完，请明天再来」，
> 这说明该账号**有额度但当天已用完**，与「完全没额度」不同，次日可再试。

### 本机工具链现状（2026-11-11 实测）

| 工具 | 状态 | 说明 |

|------|------|

| `jadx` / `apktool` / Java | 缺失 |

因此 `inspect-android-package` / `decode-android-resources` 等命令全部返回
`capability_unavailable`（`windows_native_artifact` / `runtime_missing`）。
结论：**Android 静态分析走 androguard，不依赖 REA**。
REA 剩余的可用能力是它不依赖 native 组件的 MCP 分析命令。
